# IT日常管理工作方法与SOP

**文件性质**：可直接试运行、再按公司授权批准的管理方法模板。

**建议文件负责人**：IT负责人；批准人：分管领导；版本：v1.0模板。

**适用范围**：日常IT运营、团队、需求项目、信息安全、资产、供应商和费用管理。

**配套工具**：[IT负责人日常工作台.xlsx](<IT负责人日常工作台.xlsx>)。

**入职阶段参考**：[IT负责人从入职到持续运营操作指南.md](<IT负责人从入职到持续运营操作指南.md>)。

> 本文件的频率、分级和时限均为建议起点，需结合公司业务时间、行业义务、团队及合同能力批准后实施，不代表公司已具备24小时值守能力。它是一套长期工作方法，而不是全部技术操作规程；具体系统执行命令应另编受控操作手册。

## 1. 日常管理的基本规则

你的核心职责是：**看运行、控风险、排工作、促交付、管成本、建团队、向上推动决策**。

执行七条规则：

1. **一个入口**：报障、服务请求和需求进入公司批准的统一渠道；紧急事件先电话升级，再补记录。
2. **一个主记录**：同一事项只有一份事实源，其他表只引用ID；不要在邮件、群聊、多个附件中分别维护状态。
3. **一个最终负责人**：可以多人协作，但每个行动和决策必须有明确的责任人。
4. **没有下一步不算跟进**：每个未关闭事项都有具体动作、执行人及时间。
5. **没有证据不算完成**：发出邮件、供应商口头说完成、系统可以登录，都不是充分验收。
6. **例外必须留痕**：风险接受、紧急变更、延期和超预算均按授权批准，有有效期或复核点。
7. **先恢复业务，再消除根因**：事件恢复与问题根治分别跟踪；安全事件须兼顾证据保全及合规义务。

### 1.1 四种责任不要混淆

| 角色 | 主要责任 | 不应被替代的决策 |
|---|---|---|
| IT负责人 | 技术与运营组织、风险识别、资源协调、执行监督 | 不代替业务确认收益、数据口径和流程归属 |
| 业务/流程负责人 | 业务优先级、停机影响、用户参与、验收和收益 | 对业务影响及验收结论负责 |
| 执行人/供应商 | 按批准方案执行、报告问题、提交证据 | 不自行扩大范围、权限或费用 |
| 授权审批人 | 预算、风险接受、重大变更及资源取舍 | 决策必须可追溯；具体权限按公司制度 |

小团队可兼任，但必要的审批制衡不能因兼任而自动取消。没有内部能力时，将责任落实到可考核的外包服务，而不是把系统交给无人监督的供应商。

## 2. 建立你的日、周、月、季、年日历

### 2.1 每日动作表

建议按公司业务开始/结束时间设置，不要求照搬固定钟点。

| 时点 | 动作 | 怎么做 | 留下什么 |
|---|---|---|---|
| 开工后15分钟 | 看运行 | 检查关键告警、备份失败、P1/P2事件、核心服务和昨夜变更；必要时联系值班人员 | 异常进入事件表；没有异常不虚构巡检结论 |
| 随后10分钟 | 排当天工作 | 筛选逾期、今日到期和阻塞任务；选三项最重要交付，给突发工作留缓冲 | 任务表的下一步和当日优先级 |
| 工作中 | 受理与分流 | 区分事件、服务请求、问题、变更、需求；紧急事项按升级链处理 | 工单/任务ID、负责人、时限 |
| 工作中 | 检查关键节点 | 只追关键交付和风险；需要帮助时及时解除依赖，不逐项干预技术细节 | 关键决策或阻塞处理记录 |
| 下班前10分钟 | 更新与交接 | 更新结果、证据、未完成原因、下一步；对跨时段事件明确接手人 | 状态真实的任务表、必要的交接记录 |

**每天问自己五个问题**：业务现在安全吗？今天最重要的交付是什么？谁被阻塞？有没有需要领导拍板的事情？今天的完成是否有证据？

### 2.2 每周动作表

| 动作 | 建议安排 | 议程与结果 |
|---|---|---|
| 团队周计划 | 周初30分钟 | 看上周承诺、当周容量、前三重点、依赖和风险；确认负责人、截止日及验收 |
| 需求/项目协调 | 每周或双周30—45分钟 | 由业务参与排序；处理范围变化、关键里程碑及资源冲突 |
| 风险与问题复查 | 每周20分钟，可并入周会 | 高风险、逾期、重复故障、未关闭恢复缺口；确认行动或升级 |
| 供应商跟进 | 活跃项目/问题按周 | 核对交付物、缺陷和SLA；不要只听“正在处理” |
| 一页周报 | 周末前 | 本周结果、运行风险、项目预算、需决策、下周三项承诺 |
| 知识整理 | 预留固定时间 | 把高频问题或新系统操作整理成可复用手册，并由他人抽样复现 |

无需为每一项都开独立会议。小团队可合并成一次45分钟周会；没有决策、风险或依赖的状态更新用异步方式完成。

### 2.3 每月/每季/每年动作表

| 周期 | 管理主题 | 操作及输出 |
|---|---|---|
| 每月 | 服务运行 | 复核可用率、事件、SLA及重复问题；给前3项问题分配根治行动 |
| 每月 | 合同与预算 | 看未来90天到期合同/证书/许可证；核对已发生、已承诺未发生及全年预测 |
| 每月 | 安全和权限 | 审查异常高权限、离职遗漏、补丁漏洞及日志告警；按风险安排正式权限复核 |
| 每月 | 容量与资产 | 核对关键容量趋势、云闲置资源、资产流转和维保；处理预计资源不足 |
| 每月 | 项目与收益 | 比较批准基线，复核已上线项目的采用和业务收益，不只看进度百分比 |
| 每月 | 人员与能力 | 团队工作量、加班、单点依赖、一对一反馈及技能提升 |
| 每季 | 路线图与业务回访 | 重新对齐经营目标，调整排序、资源和风险；回访关键部门 |
| 每季 | 供应商和权限 | 供应商评分、访问权限复核；高风险对象频率可更高 |
| 按批准计划 | 恢复/应急演练 | 按关键性和义务演练；关键系统变更后必要时重新验证 |
| 每年 | 规划与预算 | 总结实际收益、风险、生命周期和能力缺口，形成下一年度预算/路线图 |
| 每年及重大变化时 | 制度与适用义务 | 会同法务/合规复核制度和行业义务；经营范围变化不能等年底 |

**月底关账式检查**：所有P1/P2都有状态解释；高风险都有责任人与期限；合同到期有人决策；费用与财务一致；项目偏差有措施；所有例外有有效期；下个月的关键动作进入任务台账。

## 3. 工作分类与流转

| 类型 | 识别方法 | 主记录 | 关闭条件 |
|---|---|---|---|
| 事件 | 原本应正常的服务故障或降级 | 运维事件 | 服务恢复，业务/用户确认，必要后续已关联 |
| 服务请求 | 开账号、安装批准的软件、申请设备等标准服务 | 工单平台；暂未部署时用任务台账 | 审批合规、交付及用户确认 |
| 问题 | 重复事件或需要根因研究的隐患 | 任务台账，事项注明“问题管理”，关联事件ID | 原因及永久措施有验证，或有批准的风险处置结论 |
| 变更 | 对生产系统、配置、权限或流程的受控修改 | 变更记录 | 实施和验证结束，配置/文档更新，失败已回退或另立事件 |
| 需求 | 业务期待新增或改善的能力 | 需求池 | 实现并验证，或明确拒绝/搁置并告知原因 |
| 项目 | 需跨部门、预算和阶段交付的工作 | 项目台账 | 业务验收、运维移交、合同义务处理；收益继续复盘 |
| 风险 | 尚未发生但可能损害目标的不确定事项 | 风险台账 | 措施有效并获确认，或有权接受且持续复核 |

**分流例子**：“电脑打不开”是事件；“申请一台电脑”是服务请求；“相同型号反复坏”进入问题管理；“批量升级终端”是变更；“建立设备自助申请流程”是需求，复杂时立项。

## 4. SOP-01：事件和服务请求管理

### 触发
收到报障、监控告警、用户请求或供应商通知。

### 操作步骤

1. **登记**：受理时间、报告人、服务/系统、症状、影响范围、证据摘要；未知信息标待核验。
2. **分级**：根据影响范围和业务紧迫性判定，不根据提出者职位判定。建议P1为关键业务全面中断/疑似重大安全事件；P2为重要功能或部门明显受影响且替代方式有限；P3为一般单用户问题或可正常绕过的问题；P4为一般咨询或非紧急请求。公司可调整。
3. **指派**：一个事件负责人协调到底；转给供应商不代表IT责任结束。
4. **响应与沟通**：P1立即启动已批准的电话升级链；具体响应及沟通频率按服务级别表执行。建议重大事件约定每30—60分钟更新一次事实及下一次更新时间，需先确认资源能力。
5. **处置**：使用授权和受控手册；涉及生产改动走变更或紧急变更；必要时保全证据。
6. **验证**：技术验证后由业务确认关键功能，记录恢复时间，不以“重启完成”为恢复证明。
7. **关闭与关联**：用户确认，记录原因/暂未知、措施和后续；重大或重复事件必须创建根因行动。

### 升级条件
业务影响扩大、临近约定时限仍无进展、需要跨部门资源、疑似泄露、无法联系责任人、无可行恢复方案，均及时升级。法定通报/对外披露由授权管理层和法务/合规处理。

### 记录模板

```text
事件ID：
首次发现/受理时间：
影响系统/业务/范围：
级别及依据：
事件负责人/处置人：
已确认事实 / 尚不清楚的信息：
当前措施 / 风险 / 需审批事项：
下一次更新时间：
恢复时间 / 业务验证人及结果：
根因结论或待调查事项：
后续任务ID / 证据链接：
```

## 5. SOP-02：重复问题与重大故障复盘

**触发**：重大事件、重复发生、原因未知且风险高、SLA持续不达标。

1. 先核对时间线，区分事实、假设和缺少的证据，不以追责会议代替分析。
2. 分析直接原因、促成因素以及为何监控/测试/控制未提前发现。可用“五个为什么”，但不为了凑五层而臆测。
3. 分开记录临时绕过和永久措施；每项措施有负责人、截止日、验证方法。
4. 评估是否有同类系统/分支受影响，避免只修一个点。
5. 在约定观察期检查是否复发、指标是否改善，然后由责任人批准关闭。

建议重大故障恢复后2个工作日内形成初步复盘、5个工作日内明确行动计划；取证复杂时说明原因并滚动更新，不强求无证据的根因结论。

**复盘输出**：摘要、影响、时间线、原因及证据、有效/失效的控制、行动表、同类排查、验证结果。永久措施延期须进入风险复查。

## 6. SOP-03：生产变更与发布

**触发**：系统升级、补丁、网络/数据库/接口配置、生产权限调整、迁移、部署等。

1. 提交变更单：原因、对象、范围、执行人与时间窗口。
2. 评估依赖与影响：业务高峰、其他变更冲突、数据/权限、安全、资源。
3. 准备测试证据、备份及可用恢复点、回退步骤、判据、执行负责人和最长决策时间。
4. 取得相应审批；通知受影响部门及供应商，明确谁最终决定是否继续。
5. 按步骤执行并记录时间与结果，偏离方案或达到回退判据时停止并升级。
6. 技术及业务验证；更新配置/文档/监控；完成观察后关闭。

**紧急变更**：仅走已批准的应急授权路径，不等于无审批、无记录。事中尽量保留执行轨迹，建议下一工作日补全记录并复核；具体时限按公司制度。

### 上线前检查清单

- [ ] 业务负责人、执行人、审批人和验证人明确。
- [ ] 范围、停机窗口及受影响对象已通知。
- [ ] 测试通过，关键缺陷已处理或按权限批准例外。
- [ ] 备份/恢复点及恢复依赖可用。
- [ ] 回退条件、步骤、负责人和时间明确。
- [ ] 监控、日志、支持与供应商可用。
- [ ] 数据迁移有核对和业务确认办法。
- [ ] 操作手册、培训及移交资料已准备。

缺少关键批准、无可行回退且风险不可接受、核心数据无法核验时，暂停上线；不能用“领导很着急”代替风险决策。

## 7. SOP-04：账号、权限与入转离职

**触发**：HR人员变动、角色变化、临时访问申请、供应商进出、定期复核。

1. 由HR或授权申请人触发，核对人员、岗位、时间与主管。
2. 依据岗位权限矩阵和最小权限审批；高权限、财务敏感权限和外包访问按额外规则处理。
3. 使用个人可追溯账号；服务账号有业务/技术负责人；临时权限设到期日。
4. 按批准执行，确认MFA、访问范围及必要审计；不得在工作台存储密码、令牌。
5. 调岗回收旧权限；离职按HR批准的时间撤销访问、处理设备及数据交接，并检查云平台、VPN、业务系统、外包账号等遗漏。
6. 服务账号和共享资源先核查依赖，再停用/轮换；不要直接删除导致业务中断。
7. 定期由系统业务负责人复核权限合理性，IT执行调整并保留证据。

**交付证据**：授权工单、执行记录、复核签认、例外及到期日。离职账号保留、邮件转交、数据导出和删除须遵守公司制度及适用义务。

## 8. SOP-05：备份、恢复和连续性

### 日常检查
检查计划是否全部执行、失败/遗漏是否有处理、容量及保留是否达标、异常是否及时告警。绿色作业状态不能替代恢复验证。

### 恢复验证步骤

1. 与业务确认系统关键性、RTO和RPO，明确演练范围及成功标准。
2. 准备隔离环境、授权、样本和敏感数据控制；不得未经审批在生产覆盖恢复。
3. 选择备份点，恢复数据、配置、附件和必要依赖，记录耗时和遇到的问题。
4. 核对数据完整性、应用功能及业务结果；记录实际数据缺口。
5. 对照批准目标形成结论，未通过项进入风险及任务台账。
6. 更新操作手册，下次由另一名有权限人员抽样执行，验证知识可交接。

**中断应急方法**：事件指挥 → 评估影响 → 按授权决定切换/人工替代 → 周期沟通 → 业务验证恢复 → 对账补录 → 复盘。切换和恢复回切均要明确决策人，不能只写“IT处理”。

## 9. SOP-06：需求、项目和业务收益

1. 需求入池：必须写业务问题、证据、业务负责人、范围、当前基线和希望结果。
2. 澄清：判断是否可通过培训、流程优化、现有配置解决；避免默认购买新系统。
3. 排序：硬性义务/重大风险先识别；其他需求比较价值、工作量、依赖和资源，业务参与取舍。
4. 立项：明确范围和不做范围、验收、负责人、预算、资源和里程碑。
5. 执行：每周只看实际交付物、关键路径、风险和偏差；百分比必须有可验证定义。
6. 范围变更：记录新增内容、收益、工期/成本影响，批准后修改基线，保留历史。
7. 上线与验收：通过测试、变更和业务验收，运维接收支持资料，不把上线当天当作项目收益实现日。
8. 收益复盘：上线后30/60/90天按适用周期对比基线，业务负责人确认，未达标继续优化或决定停止投入。

**项目周检六问**：本周交付了什么？下个里程碑是否能守住？关键阻塞是什么？范围变了吗？成本预测变了吗？需要谁何时做什么决定？

## 10. SOP-07：资产、合同、供应商和费用

### 资产闭环

申请审批 → 采购与验收 → 编码入账/入台账 → 领用配置 → 维修/调拨 → 归还 → 合规数据清除及报废。IT、行政和财务分工确认；序列号/云资源ID应能与责任人和关联系统对应。

资产流转即时更新、关键资产定期核验、全面盘点按财务与公司周期安排。云资源也属于管理范围，需要归属、标签、预算和回收机制。

### 合同与续费

- 每月查看未来90天到期项；遇到提前通知条款长于90天的，按更早期限设置任务。
- 核对合同到期日与“最迟续约/解约通知日”，二者不是同一天。
- 续费前问：实际使用量如何？服务达标吗？仍需要吗？能否合并或降配？不续费如何导出数据与切换？
- 提前安排预算、审批、谈判和技术验证，不能临到期才让领导付款。
- 许可证、域名、证书、运营商线路、云预付额度也应纳入提醒。

### 供应商管理

每个供应商指定内部负责人，按服务可用性、响应/解决、交付质量、安全与文档、成本、配合程度评价。根据事实和合同讨论整改，不仅凭个人印象打分。关键供应商保留替代/退出方案、公司拥有的账号与文档，避免全部控制权在个人或外部手中。

### 费用检查

核对四项：预算、已发生、已承诺未发生、预计新增。全年预测一般为后三项之和；“已支付”属于已发生的付款情况，不重复相加。币种、含税口径及财务确认一致后再汇总。无预算或超预算按审批权限处理，不拆单绕审批。

## 11. SOP-08：安全风险、漏洞和例外

1. 收到告警/漏洞/审计发现，先确认范围、证据和是否正在被利用；正在发生的事件走事件流程。
2. 结合业务暴露、数据、可利用性及已有控制评级，不只照抄扫描工具分数。
3. 指定风险负责人及技术执行人，确定临时控制、长期措施和期限。
4. 修复需测试与变更；无条件立即修复时，提出隔离/访问限制等补偿控制，并由有权人员批准。
5. 修复后复测，确认问题确实消除及业务未受损，再关闭。
6. 例外保留理由、残余风险、批准人、有效期和复核日期；到期必须重新决策，不能永久搁置。

**严禁**：未经授权扫描生产或第三方、扩大数据访问、将原始敏感资料上传未经批准的云服务、以“已接受风险”掩盖没有审批的延期。

## 12. SOP-09：团队、知识和工作量

### 分工
建立系统主责与备份责任人；每个关键系统至少有清晰的内部责任人和替代支持路径。只有一名IT时，可用受合同约束的供应商及交接文档降低单点，不假设实际存在第二名员工。

### 周度容量管理
先估算固定运维、项目和已知休假，再保留突发缓冲。将任务拆为可验收的短交付；超容量时明确延期或增援，由业务/领导做优先级取舍，不以长期加班掩盖资源缺口。

### 知识管理
高频问题、重大故障和新系统上线都应产生知识条目：适用范围、前置权限、步骤、验证、回退、风险、负责人、更新时间。由未编写该条目的有权限人员抽样验证。过期资料标记作废，不静默覆盖关键版本。

### 人员管理
每月一对一关注工作障碍、技能、协作、负荷和发展。绩效同时看服务质量、风险降低、交付效果、知识共享及协作，不单独考核工单数量或“零事故”，避免诱导隐瞒问题。

## 13. 会议工作法与向上管理

### 13.1 30分钟团队周会

- 5分钟：上周承诺与未完成原因。
- 5分钟：运行及高风险。
- 10分钟：本周三项重点、人员容量和依赖。
- 5分钟：需要决策/升级事项。
- 5分钟：逐项确认行动、负责人、截止日、验收标准。

### 13.2 月度IT经营评审（45—60分钟）

参会：分管领导、关键业务代表、IT；按议题邀请财务/采购/合规。

材料提前发出，会上只讨论偏差与决策：业务目标变化 → 服务与风险 → 项目和收益 → 预算预测 → 下月资源取舍。会议结束生成决策ID及行动，不只保存聊天记录。

### 13.3 提请决策的表达

不要只说“有风险、缺人、供应商不配合”。使用：

```text
需要决定：
事实和证据：
不决策的影响及最迟日期：
方案A：成本/时间/收益/风险
方案B：成本/时间/收益/风险
建议及理由：
需要批准的资源/范围/风险：
决策人、结论、日期：
后续行动ID：
```

领导未回复不是批准。到达决策时限仍未决定时，按既定升级链提醒并说明影响，不自行越权。

## 15. 工作台维护规范

| 管理事项 | 主表 | 更新人/时机 |
|---|---|---|
| 每日工作 | 10任务台账 | 执行人更新，IT负责人每日看重点和阻塞 |
| 故障 | 11运维事件 | 事件负责人随进展更新，紧急先沟通后补记录 |
| 风险 | 07风险台账 | 风险负责人定期确认，重大变化即时更新 |
| 生产修改 | 12变更记录 | 执行/变更负责人在审批、执行、验证时更新 |
| 权限 | 06权限复核 | 授权执行人及复核人按变动和复核周期更新 |
| 恢复验证 | 15备份恢复 | 系统/备份管理员每次检查与演练后记录 |
| 需求/项目 | 08需求池、09项目台账 | 需求/项目负责人有变化即更新，周会前核对 |
| 合同/费用 | 13供应商合同、14预算费用 | 合同负责人及财务核对，变化即更新、每月复查 |
| 决策/汇报 | 16决策记录、17周报、18指标记录 | IT负责人在决策后/每周/指标周期维护 |

若已有专业平台，以平台为主记录，仅在工作台汇总ID、风险及管理结果。证据链接必须指向公司受控位置；工作簿本身也需访问控制和备份，不把Excel保护当作权限隔离。

## 16. 前四周如何把这套方法真正跑起来

| 周次 | 只聚焦这些动作 | 成功标准 |
|---|---|---|
| 第1周 | 统一入口、任务/事件/风险表、每日检查、固定周报 | 未结重点事项均有负责人、截止日和下一步 |
| 第2周 | 加入变更、权限、合同到期和恢复管理 | 关键修改有审批；关键到期项可见；恢复缺口进入整改 |
| 第3周 | 建立需求排序、项目周检、供应商行动表 | 业务参与取舍；关键项目有验收标准和资源 |
| 第4周 | 第一次月度评审、预算预测、问题复盘与知识沉淀 | 有实际决策和闭环，不是只汇报“工作很多” |

跑完一个月后，删掉无使用价值的记录项，补上反复漏掉的字段。衡量这套方法是否有效，只看：**故障是否更可控、责任是否更清楚、决策是否更及时、交付是否更可信、业务是否确实改善。**
