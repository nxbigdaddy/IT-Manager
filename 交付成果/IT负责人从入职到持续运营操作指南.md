# IT负责人从入职到持续运营操作指南

> 适用前提：公司已有部分信息系统，但规模、行业、监管要求、IT人员和预算尚未明确。本指南提供通用执行框架，时间安排为建议，不代表对贵公司现状的判断。涉及监管、个人信息、跨境、等级保护、财务及合同义务，应请法务/合规结合实际确认。
>
> 配套文件：[IT负责人日常工作台.xlsx](<IT负责人日常工作台.xlsx>)。先用起来，再按企业实际增删；不要为了填表而填表。

## 一、先明确：你负责的不是“买系统”，而是五个结果

1. **业务能持续运行**：关键业务不中断，出现故障可响应、可恢复。
2. **风险可知、可控**：关键账号、数据、网络、供应商和人员单点有人负责。
3. **花钱有依据**：预算、合同、许可证、续费、项目成本透明。
4. **业务效率可改善**：需求能排序、项目能交付、效果能验证。
5. **管理可持续**：责任清楚、过程留痕、人员可交接，不依赖个人记忆。

你的工作有三条并行主线：日常运营、安全与连续性、业务改进。不要等“资产全部盘点完”才处理高风险，也不要因为一直救火而放弃治理。

### 入职时必须向领导确认的10件事

- 公司未来一年最重要的三项经营目标是什么？
- 当前最不能停的三个业务环节是什么？停一小时会影响什么？
- 领导对IT最不满意、最希望优先改变的事情是什么？
- 哪些业务/系统/地点/子公司属于你的管理范围？哪些暂不属于？
- 你对人员、采购、供应商、账号、安全、变更分别有多大权限？
- 有多少内部人员、外包服务能力和可用预算？有哪些冻结或限制？
- 近期是否有审计、投融资、开店、搬迁、系统上线、客户检查等硬节点？
- 谁是业务流程负责人、数据负责人、系统业务负责人及最终验收人？
- 发生重大故障或安全事件时，谁决定停机、对外沟通和风险接受？
- 你每周向谁汇报、每月由谁决定跨部门优先级？

**产出**：一页《IT工作授权与90天目标》。至少写明范围、资源、前三项结果、决策机制和汇报节奏，请直接上级确认。未获授权前，不擅自扩大数据访问或生产变更范围。

## 二、从第一天到全年：按阶段推进

| 阶段 | 重点工作 | 关键交付 | 阶段通过条件 |
|---|---|---|---|
| 第1—3天 | 获得授权；建立紧急联系人；识别关键系统；检查迫近的续费/证书到期、离职高权限账号、备份告警 | 授权确认、关键业务/系统初表、紧急联系人、首批风险 | 关键系统有负责人及联络方式；紧急风险已处置或进入有责任人/期限的升级机制 |
| 第4—10天 | 访谈管理层与关键部门；跟岗观察；收集资产、合同、网络、系统、账号、备份证据 | 现状清单v0.1、痛点清单、风险台账、依赖草图 | 关键业务得到覆盖；资料缺口和未核验事实清晰可见 |
| 第11—30天 | 核验现状；建立工单、权限、变更、备份等最小机制；验证恢复；做1—3个低风险快赢 | 现状诊断、风险分级、30天报告、快赢结果 | 重大风险有方案；关键恢复能力有验证或明确缺口；形成领导认可的优先级 |
| 第31—60天 | 设计目标流程和总体方案；排需求；评估自建/购买/优化；测算总成本；试点 | 需求池、6—12月路线图、预算草案、试点及验收标准 | 业务负责人签认需求及指标；每个拟立项项目有资源、验收人和决策结论 |
| 第61—90天 | 试点上线和效果复盘；完善运维交接、制度和团队分工；按业务波次推广 | 首批项目交付、操作手册、服务目录、90天总结 | 上线有验收、回退、培训和支持；下一阶段资源/路线图获确认 |
| 第4—6个月 | 推广有效试点；治理数据和接口；补齐监控、权限复核与连续性能力 | 阶段项目收益报告、数据标准、服务运行报告 | 核心指标较基线改善；新增系统已纳入运维与资产管理 |
| 第7—12个月 | 持续优化、技术债清理、审计整改、供应商评价、年度预算与战略滚动 | 年度成效、年度风险回顾、下一年规划 | 收益、成本、风险和能力缺口都有证据及明确下一步 |

时间可以缩放：小公司兼任IT时，优先做关键系统、恢复、账号、合同和需求；多区域/制造/金融等复杂企业，应设置分阶段发现与分域负责人，不承诺30天完成所有详细盘点。

### 第一周照着做

| 日程 | 具体动作 | 当天记录/产出 |
|---|---|---|
| 第1天 | 与老板确认授权和目标；与现有IT/外包交接；拿到故障升级链和关键联系人；检查未来30天到期项 | 当日任务、初始风险、授权待确认项 |
| 第2天 | 走查关键业务和机房/网络；通过授权的只读方式了解核心系统与备份；核对管理员归属 | 关键系统初表、恢复能力缺口、关键账号责任人 |
| 第3天 | 访谈财务、人力、销售/业务负责人；收集审批/入离职/采购/报表真实样本 | 访谈纪要、痛点及证据、流程草图 |
| 第4天 | 访谈运营/生产/仓储等适用部门；核对合同、许可证和外包边界；召开风险短会 | 收集清单状态、风险处置任务、供应商到期提醒 |
| 第5天 | 整理一页周报；确认前三优先事项和下周资源；选择一个低风险快赢 | 第1周周报、领导决策、下周任务 |

不要在第一周为了“证明能力”直接重建网络、升级ERP、删除账号或大批量切换权限；先确认业务依赖、备份、影响、审批和回退。

## 三、信息收集：收什么、找谁、怎么收、要什么证据

### 3.1 统一采集方法

采用“四步核验”：**问（访谈）→ 看（业务实际操作）→ 查（配置、报表或合同）→ 验（抽样、演练或交叉核对）**。

一条信息至少记录：类别、对象、负责人、来源、截至日期、事实描述、证据链接、可信状态、缺口、下一步、截止日。

- 可信状态统一为：未收集、已收集待核验、已核验、存在冲突、不适用。
- 没有证据时写“未核验”，不要默认“没有风险”。两份资料不一致时保留来源，找责任人确认。
- 优先关键业务和高风险对象，再逐步补全长尾资产；覆盖率必须先定义范围和分母。
- 生产检查优先只读；扫描、渗透测试、恢复、切换、权限变更均须事先授权并限定时间、范围及影响。

### 3.3 信息请求如何发给各部门

可复制以下模板：

> 为在不影响正常业务的前提下完成IT现状摸底，请贵部门指定一位对接人，并在【日期】前提供【资料名称/范围/截至日期】。用途为【风险识别/业务优化等】，通过【公司批准的受控资料库】提交，不通过普通群聊发送敏感资料。若无现成材料，请回复“暂无”、现负责人及建议访谈时间，不要求为本次收集重写全部文件。涉及个人信息请提供最小必要、脱敏样本；密码、密钥、令牌不得提交至工作台或普通附件。我们将于【日期】与资料责任人共同核验并确认缺口。

### 3.4 访谈怎么问

每次30—45分钟，先理解业务，不先演示产品。建议问题：

1. 您部门的三项关键结果是什么？依赖哪些数据和系统？
2. 从业务开始到结束，请用一个真实但脱敏的案例走一遍。
3. 最费时、出错最多或重复录入的三个步骤是什么？频率和影响多大？
4. 系统停多久会不可接受？哪些数据丢失不可接受？现有人工预案是什么？
5. 哪些报表数字经常对不上？最终以谁确认的口径为准？
6. 如果只能改善一件事，优先哪件？您愿意提供谁、多少时间参与？
7. 如何证明改善有效？现有基线是什么？谁验收？

会后一个工作日内回发纪要，区分“已确认事实、个人意见、待核验问题、决策、行动”。不要把一次访谈的愿望直接变成立项承诺。

## 四、诊断与排序：从资料变成可执行决策

### 4.1 给老板的现状诊断只回答六件事

- 现在哪些能力支撑哪些经营活动？依赖关系是什么？
- 哪些问题会导致停业、数据丢失、合规或重大财务损失？
- 业务效率卡在哪里？有多少频次、时间、损失的证据？
- 已有资源能解决什么？哪些必须外部采购或追加资源？
- 未来90天先做什么、不做什么、为什么？
- 需要老板批准什么：责任人、预算、停机窗口、跨部门投入或风险接受？

### 4.2 两套排序，不混用

**风险排序**：可能性1—5 × 影响1—5，结果1—25分；建议20—25紧急、12—19高、6—11中、1—5低。评分只是讨论工具，重大正在发生的事件、明确法定期限、关键系统无可恢复副本等，可经业务/安全负责人确认直接提升，不等评分会议。影响至少考虑业务中断、数据、安全合规及财务；评分尺度由公司统一。

**需求排序**：业务价值、覆盖/频次、紧迫性、风险降低各1—5分，建议价值分为35%×业务价值＋20%×覆盖频次＋20%×紧迫性＋25%×风险降低，再除以粗估工作量（人周，必须大于0）辅助排序。初期也可直接用“必须/应该/可以/暂不做”四档。工作量、前置依赖和资源不明确时不承诺排期。

合规硬期限、重大风险整改先过强制门槛；其余比较投入产出。避免通过拆分极小任务人为抬高排序。最终优先级由业务决策机制确认，而不是由IT或打分公式独断。

### 4.3 快赢的选择

优先选2—4周内可完成、可回退、不改变关键交易逻辑、效果可量化的事项，例如：建立单一报障入口、续费提醒、员工入离职核对、重复报表自动化、经审批修复明显的权限缺口。涉及删除账号、改权限或自动化执行仍须确认依赖和审批。

每个快赢写清：问题证据、基线、目标、负责人、时间、验收人、风险/回退。不要把采购金额和上线数量当作收益。

## 五、整体信息化推进：从业务目标到上线收益

### 5.1 总体路径

**经营目标 → 业务能力与流程 → 数据标准 → 系统/集成方案 → 试点 → 推广 → 运营和收益复盘。**

常见的推进顺序是“补齐安全及基础运维 → 打通关键业务流程 → 统一关键数据/接口 → 管理分析 → 更高级自动化或AI应用”。这不是固定采购顺序，应按公司瓶颈、依赖和风险调整；原有系统能满足时优先配置优化和流程改进。

规划至少形成四张图：业务流程图、应用及系统依赖图、数据流/接口图、基础设施和安全边界图。当前与目标分开画，不必初期追求复杂制图工具。

### 5.2 每个项目必须经过的关口

| 关口 | 如何做 | 通过证据与责任 |
|---|---|---|
| G0 需求进入 | 记录业务问题、样本、影响、业务负责人；排除培训或现有配置即可解决的事项 | 需求单；业务负责人确认问题成立 |
| G1 价值及立项 | 明确范围/不做范围、基线目标、成本、依赖、资源、风险和替代方案 | 立项书、预算、验收指标；业务发起人/授权审批人批准 |
| G2 方案及采购 | 比较现有系统优化、自建、购买、外包；核验架构、数据、安全及退出路径 | 方案评审、选型评分、合同条款；业务/IT/采购/法务按职责批准 |
| G3 构建与验证 | 配置/开发、接口测试、权限测试、脱敏测试、数据迁移试跑、用户验收 | 测试与缺陷记录、迁移对账、UAT签认；关键缺陷关闭或明确例外 |
| G4 上线准入 | 培训、上线窗口、备份、回退判据/时限、回退负责人、应急支持、通知 | 上线清单、变更批准、业务确认；高风险遗留不可静默放行 |
| G5 验收移交 | 核对范围、性能/安全/业务指标；运维接管文档、账号、监控、许可证 | 验收单、遗留问题期限、支持及知识转移；业务验收、IT运维接收 |
| G6 收益复盘 | 上线后30/60/90天按同口径比较基线，审查采用率及新风险 | 收益报告；业务负责人确认，未达标进入优化或停止决策 |

一个项目至少有四个角色：业务发起人（收益和流程负责）、项目负责人（交付协调）、IT技术负责人（技术及运行负责）、验收人（确认业务结果）。小公司可兼任，但提出、审批、验收等必要制衡按公司权限规则保留；关键决策至少指定唯一最终拍板人。

### 5.3 选型和合同不要漏掉这些

- 先用真实场景脚本演示，再比较价格；不要只看产品展示。
- 计算3年总拥有成本TCO：许可/订阅、实施、接口、数据迁移、基础设施、内部投入、培训、维保升级、安全合规及退出成本；含税/不含税口径一致。
- 验证扩展性、接口开放性、数据导出格式、备份恢复、权限审计、供应商持续服务能力。
- 合同明确交付物、里程碑付款、验收标准、SLA、数据归属、保密、安全责任、违约、源代码/配置等约定交付、终止与迁移支持。具体法律条款由法务审核。
- 合同签订不等于项目启动条件齐备；必须先确认业务参与资源。

## 六、建立最小可用管理机制

### 6.1 先落地八项机制，不先写厚制度

| 机制 | 最低做法 | 支撑文件 |
|---|---|---|
| 事件/服务请求 | 单一受理入口；分级；责任人；升级链；记录恢复与用户确认 | 服务目录、工单规范、紧急联系人及SLA |
| 问题管理 | 对重复/重大故障分析根因，验证永久措施效果 | 故障复盘与问题清单 |
| 账号权限 | 入转离职有审批；按角色最小权限；高权限MFA；定期复核 | 权限矩阵、申请/撤销工单、复核记录 |
| 变更发布 | 明确影响、测试、审批、窗口、通知、回退与验证；紧急变更补审计记录 | 变更单、发布/回退清单 |
| 备份恢复 | 有范围、周期、保留、隔离和告警；按关键性定期恢复验证 | 备份策略、运行记录、恢复演练报告 |
| 资产及配置 | 新购/领用/归还/报废及配置变更同步台账，指定责任人 | 资产台账、配置库、处置记录 |
| 供应商及合同 | 合同、续费、验收、服务质量和退出资料定期审查 | 合同台账、评价表、交付物索引 |
| 需求/项目治理 | 统一入口、定期排序、变更控制、业务验收、收益复盘 | 需求单、项目章程、路线图、验收及复盘 |

制度编制顺序：先画一页流程、明确谁做/谁批/保存什么证据，试运行2—4周，再固化制度。每份制度写明负责人、适用范围、版本、批准人、生效日期和复核周期。

### 6.2 故障与安全事件如何处理

1. 确认影响范围、时间和业务；重大事件立即启动升级，不等周会。
2. 指定事件指挥、技术处置、业务沟通、记录四种职责。
3. 优先安全地恢复服务；疑似安全事件同时保全证据，避免擅自删除日志或扩大访问。
4. 按约定周期更新“已知事实、影响、正在做什么、下次更新时间”，不承诺无依据的恢复时间。
5. 恢复后由业务验证；重大/重复问题做根因分析并跟踪改进，不以重启成功等于根因消除。
6. 是否触发法定报告、对外披露、个人信息通知等，由法务/合规依据适用义务判断。

事件分级和响应时间应与业务商定。示例：关键业务全面中断或疑似重大泄露为P1并立即电话升级；具体24×7值守和恢复承诺必须有人员、合同与能力支撑，不把示例当作已批准SLA。

### 6.3 备份成功不等于可恢复

- RTO是目标恢复时间，RPO是可接受的数据丢失时间窗口，由业务影响分析提出并与成本能力协调确认。
- 恢复演练必须记录：对象、备份时间点、环境、批准、实际恢复耗时、实际数据时间点/缺口、校验、业务验证、结论及整改。
- 选择代表性系统在隔离环境恢复，检查数据库、附件、配置、密钥依赖和应用完整链路，不只看文件存在。
- 生产切换/灾备演练是另一个风险级别，需要单独审批、窗口与回退。未演练时明确写“恢复能力未验证”。

## 七、日常工作方法：一个入口，四张常用表，固定节奏

配套工作台共20个工作表。日常只需要常开 **任务台账、运维事件、风险台账、周报**；需求、项目和基础台账按有变化时更新。其他表用于初始化、月度或阶段治理，不要求每天全填。

### 7.1 每天：15分钟计划＋10分钟收尾

- 上午：看关键告警、备份异常、P1/P2事件、今日到期和被阻塞任务，选当天最重要三件事。
- 新任务统一记录：ID、来源ID、事项、负责人、截止日、状态、下一步、证据。聊天中的承诺也要入表。
- 时间安排保留突发事件缓冲；如果连续两周全部时间被救火占满，向领导提出资源/优先级调整。
- 下班前：更新完成和阻塞，明确明天第一步。不要只写“持续跟进”，应写“周三与财务确认三份对账样本，产出差异清单”。

### 7.2 每周：运维短会＋需求/项目协调＋一页周报

- 检查上周承诺、当前风险、里程碑和资源依赖；没有责任人/截止日的行动不算会议结论。
- 需求排序会议可按需求量每周或双周一次，业务参与，不让IT独自背业务取舍。
- 周报结构：本周结果（带证据）、关键指标、重大风险/阻塞、需要决策、下周前三件事。
- “需决策”必须写：选项、建议、资源/费用、最迟决策日期、不决策影响。

### 7.3 每月、每季、每年

| 周期 | 必做动作 | 输出 |
|---|---|---|
| 每月 | 预算/账单、合同续费、SLA、风险逾期、项目收益、权限异常、资源容量复核 | IT月报、滚动任务及预算预测 |
| 每季 | 路线图重排、业务满意度回访、供应商评价、访问权复核、按计划恢复演练 | 季度成效/风险报告及调整建议 |
| 每年 | 战略对齐、预算、资产生命周期、合规范围复核、重大应急演练及制度更新 | 下一年度规划与预算、年度风险及能力评估 |

频率是起点，具体按风险、合同、监管、业务高峰和资源调整；关键告警和事件不能等周期会议。

### 7.4 台账之间如何衔接

示例（不是贵公司实际情况）：访谈发现某业务系统从未做过恢复验证。

1. 在“信息收集”标记“已收集待核验”，附备份日志及纪要受控链接。
2. 在“风险台账”创建RSK-001，写明潜在业务影响、风险负责人和临时措施。
3. 在“任务台账”创建TSK-001，来源为RSK-001，安排授权隔离恢复演练。
4. 在“备份恢复”创建BAK-001，记录目标RTO/RPO、实际结果和业务验证。
5. 如果需生产变更，关联CHG-001；如果需新增预算，进入需求REQ-001及立项，而非直接下单。
6. 验证通过并由风险负责人确认后关闭风险；未通过则保留风险并生成整改任务。
7. 周报引用ID和结论，不重复抄录全部原始信息。

## 八、指标：先有基线，再定目标

前2—4周先建立可信基线。目标由业务、IT和资源约束共同确认，不虚构“99.99%可用率”或“故障下降50%”。指标至少记录定义、范围、周期、来源、负责人和目标。

| 指标 | 建议定义 | 注意事项 |
|---|---|---|
| 关键服务可用率 | （约定服务时间－按SLA计入的中断时间）÷约定服务时间 | 服务时段及计划维护是否排除须预先约定；不同系统不要盲目平均 |
| 平均恢复时间MTTR | 已恢复事件的恢复耗时总和÷已恢复事件数 | 明确起止点，未恢复事件单列，避免通过关闭工单降低指标 |
| SLA达标率 | 周期内达成约定SLA的适用工单÷适用工单 | 明确按创建/关闭/到期时间归集及暂停规则 |
| 备份作业成功率 | 成功备份作业÷计划执行作业 | 不能代替恢复验证成功率 |
| 恢复验证通过率 | 满足完整性及约定RTO/RPO等标准的演练÷已执行演练 | 未执行的计划演练单列完成率，不隐藏在分母之外 |
| 高风险逾期数 | 截至报告日未关闭且超过整改期限的高/紧急风险数 | 风险接受要有批准人及到期复核日 |
| 项目里程碑按期率 | 按已批准基线按期完成的到期里程碑÷到期里程碑 | 重设基线需批准并保留历史 |
| 预算执行与预测 | 已发生、已承诺未发生、预计新增分别统计 | 避免重复计费；预测全年费用而非只看付款额 |
| 业务改善效果 | 同口径处理时长/错误率/人工投入相对基线的变化 | 注明样本量、业务量变化及归因限制；节省工时不直接等于现金节省 |
| 系统采用率 | 目标人群中按约定频率使用关键功能的实际用户÷目标用户 | 登录次数不等于业务采用 |

分母为零或数据缺失时显示“不适用/待采集”，不要填0%冒充测量结果。配套工作台提供指标口径与人工记录，不含自动计算看板，避免未填写的数据产生误导。

## 九、文档怎么管，避免一堆散表

建议在公司批准的受控共享盘/文档平台建立目录（这些是建议结构，不是已创建的实际资料）：

```text
IT管理/
  00_授权与规划/
  01_现状与信息收集/
  02_资产系统与架构/
  03_风险安全与连续性/
  04_需求与项目/项目ID_项目名称/
  05_运维变更与知识库/
  06_合同预算与供应商/
  07_周报月报与决策/
  99_归档/
```

文件名建议“日期_对象_文件类型_v版本_状态”；状态用草稿/评审/批准/作废，保留版本记录和审批链接。索引中写责任人、访问范围、保留期限、复核日期。

**敏感信息边界**：工作台只放摘要和受控证据链接；不放密码、密钥、令牌、员工身份证信息或客户原始数据。高权限账号标识、网络架构和合同也可能敏感，按最小权限控制工作簿访问。Excel隐藏工作表、工作表保护不是安全隔离。普通只读副本也可能包含历史敏感数据，分享前单独脱敏导出。

在Excel中由一名台账管理员维护主版本，采用公司支持的协作/版本能力；多人并发频繁、出现审计或权限分域要求时，将表结构迁移至批准的工单/项目/资产平台，避免多份附件流转。不要在“Excel＋工单平台”长期双重维护同一事实。

## 十、配套工作台使用说明

- **00使用说明**：操作规范、ID、状态与数据边界。
- **01_90天计划**：预置阶段任务及验收标准；实际日期、责任人、状态由你补充。
- **02信息收集**：18类信息，明确内容、来源、方法、支撑文件和核验方式。
- **03访谈纪要**：一条结论一行，多条结论可以共用会议ID。
- **04系统台账**：系统、业务归属、依赖、RTO/RPO、供应商及数据等级。
- **05资产台账**：设备/云资源、使用人、状态、维保与处置。
- **06权限复核**：访问摘要、责任与复核证据；不存凭据。
- **07风险台账**：风险、应对、审批及残余风险。
- **08需求池**：业务问题、基线目标、排序、立项结论。
- **09项目台账**：阶段关口、里程碑、预算、验收与收益复盘。
- **10任务台账**：日常唯一行动清单；通过来源ID关联其他表。
- **11运维事件**：受理、分级、恢复、确认及根因改进。
- **12变更记录**：生产改动、审批、测试、回退与验证。
- **13供应商合同**：服务、费用、到期、提前通知及退出。
- **14预算费用**：预算与费用明细；防止已付与已承诺重复计算。
- **15备份恢复**：备份范围、恢复目标、演练结果与整改。
- **16决策记录**：选项、建议、批准人、决策和后续动作。
- **17周报**：一周一个编号，按结果/风险/决策/下周计划分行记录。
- **18指标记录**：预置口径，填基线和实际值；不预设目标。
- **19填写示例**：与正式台账隔离的虚构演示，不计作公司现状。

工作簿中的正式台账保持空白；90天计划、信息清单、指标为通用模板。可新增行；预设筛选和常用下拉覆盖至第501行，超过后请扩展表格/校验范围。日期使用Excel日期值，金额使用数值，单位在字段或备注中说明。不要删除ID后复用，应将取消/作废事项保留并说明原因。

### 完成/关闭的定义

- 任务完成：交付物存在，验收人或需求方确认，不是“已发邮件”。
- 风险关闭：控制措施生效并有验证；仅改变截止日不算关闭。接受风险必须由有权责任人批准并设置复核日期。
- 需求完成：交付并验证业务结果；不实施的需求记录拒绝/搁置原因。
- 项目完成：业务验收、运维移交、文档与合同义务处理完毕；收益复盘仍按计划跟踪。

## 十二、常见错误与停止条件

- 先买产品，再找业务用途 → 改为先问题、基线、流程和验收标准。
- 全部问题都列最高优先级 → 明确必须做、可以延期、不做的取舍，并让业务共同确认。
- 只收口述，不核验 → 至少为关键事实建立文档/后台/抽样证据。
- 备份显示绿色就认为安全 → 做恢复验证并对照RTO/RPO。
- IT独自定义流程和数据口径 → 业务/数据负责人拍板，IT提供技术与方法。
- 只报工作量不报结果 → 报告风险是否降低、业务是否改善、证据是什么。
- 只有建设没有运维预算 → 立项时同时计算3年运行和退出成本。
- 无资源却承诺所有项目 → 暂缓低优先级事项，要求授权人做资源取舍。

**以下情况先暂停上线或扩大实施**：没有业务负责人/验收标准；没有授权的数据访问；关键生产变更无可行回退；关键缺陷无处置结论；预算未获必要批准；供应商无法说明数据归属和退出方式。对确需例外的情况，记录影响、补偿控制、批准人和到期日，不能自行默许。
