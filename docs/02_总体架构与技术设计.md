# 02 总体架构与技术设计

## 架构
```text
Windows PySide6桌面
  ├─导航/表格/表单/看板/草稿审核
  └─异步API客户端（认证、超时、错误归一化）
             │ 本机HTTP；远程HTTPS
Python FastAPI服务端（单实例）
  ├─业务服务：规划、任务、考核、台账、汇报
  ├─AI适配：DeepSeek / Kimi / Qwen
  ├─消息适配：群机器人 / SMTP
  ├─调度器：到期触发、持久化发送队列、结果审计
  └─数据访问与审计
       ├─SQLite（业务、配置引用、草稿、调度、审计）
       ├─受控密钥存储/服务器环境变量
       └─备份与受控导出目录
```

## 技术选择
- GUI：PySide6。主窗口QMainWindow、导航QListWidget或QTreeView、内容QStackedWidget；台账QTableView＋模型及排序筛选代理；表单QDialog。
- 耗时操作：QThreadPool/QRunnable或Qt异步网络。工作线程不直接访问控件，只通过信号更新主线程。所有网络操作有超时，防重复点击。
- 服务：FastAPI＋Uvicorn，REST JSON。桌面不直连数据库、不自行调用第三方凭据。
- 数据：首版SQLite WAL，短事务、单服务实例、乐观锁；文件只能放服务端本地磁盘，不放共享盘供多进程/多主机写入。
- 调度：首版服务进程内独立线程/任务，数据库存放计划与发送槽位；只允许一个服务工作进程。扩容时先拆持久队列及独立调度锁。
- 适配层：标准库HTTPS/SMTP，独立单元测试。PySide6依赖需检查安装，当前不假定已经可用。

## 分层约束
GUI→API客户端→路由/校验→业务服务→持久层/外部适配器。禁止GUI拼SQL、路由中沉淀大量业务规则、定时器直接绕过审批发送AI草稿。

现有原型部分逻辑集中在服务模块，后续按业务服务、调度服务、配置服务拆分；原型不作为架构豁免。

## 关键流程
1. 保存：表单校验→带版本提交→事务保存＋审计→刷新。版本冲突提示重新加载，不覆盖别人更新。
2. AI：选择记录→显示发送范围→敏感信息二次确认→调用→保存草稿及提示词版本→人工审核；不自动创建正式任务或发送。
3. 周期汇报：到期槽位幂等占位→生成确定性汇报→草稿或预先授权自动发送→记录结果。自动发送授权不扩大到AI草稿。
4. 发送：审核通过＋请求幂等ID→持久化待发送→执行→成功/确定失败/结果不确定。网络超时不等于平台未接收。

## 性能与故障边界
目标先支持单管理员、数万条记录以内的可用管理场景，必须以实际测试确定能力；列表需分页、服务端筛选，不能永久全量拉取。看板统计需定义分母和日期口径。服务不可用时显示断线与重试，不悄悄落到本地第二份数据。离线编辑与双向同步不属于首版。

## 软件供应与许可
固定依赖版本并记录运行环境；部署前检查PySide6/Qt分发许可及第三方许可证，采用满足许可义务的发行方式。打包和代码签名是后续交付工作，不承诺已生成安装包。
