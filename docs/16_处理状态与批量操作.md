# v0.6 第一波：处理状态与批量操作

## 交付内容
1. 提醒处理状态：标记已处理、稍后提醒（未来日期）、忽略（必填原因）。状态按规则+记录唯一键保存，记录当时版本；对应业务记录被修改后状态自动失效并重新提醒。“显示已处理”可回看。工作台提醒条在未加载服务端规则时仍标注按内置规则估算。
2. 体检整改跟踪：已整改、误报忽略（必填原因）；建立整改任务成功后自动记录“已转任务”。同样绑定记录版本，记录变化即重新出现，复查默认不再重复报警。
3. 批量操作：列表支持 Ctrl/Shift 多选，批量修改字段、批量顺延日期、批量归档、导出当前选择（CSV/单表 Excel）。服务端一个事务内全有或全无，逐条版本 CAS，最多200条并拒绝重复ID；同一请求编号重试不重复写入，改内容自动换新编号。

## 接口
- `GET /reminders/states`、`POST /reminders/state`；`GET /health/states`、`POST /health/state`。
- `POST /records/batch`（`{updates:[{id,version,data}],request_id}`）、`POST /records/batch-archive`（`{targets:[{id,version}],request_id}`）。
- 批量路由必须定义在 `POST /records/{module}` 之前，否则会被当成模块名（实现时已踩到并修正）。

## 修复的真实缺陷
- **提醒规则被存储元数据吞掉**：`compute_items` 对规则做严格校验，而从服务端读回的规则带 `id/version/created/updated/oldhistory`，导致全部规则被静默跳过——真实环境下提醒永远为空。现校验前剥离存储元数据，并保留对规则内容的严格校验。该问题由端到端测试（服务端→界面）发现，单元测试未能覆盖。
- 页面重建后旧控件被再次写入：体检空态与状态复选框在 `deleteLater` 后仍被旧回调访问，抛 `RuntimeError`。现所有跨页读取都经存活检查，失效即忽略。

## 边界
- 处理状态是“提示收敛”机制，不是审批：已处理不等于问题已解决，忽略仍需人工判断。
- 批量操作不校验业务合理性、不校验跨记录引用语义；批量归档不是删除，被引用时整批拒绝。
- 导出文件含业务数据，需按公司要求保管；CSV 对公式注入做了前置单引号处理。
